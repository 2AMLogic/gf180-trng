# DR-0031: Transient-noise records promise replay of the deck and configuration, not of the trnoise waveforms

## Status

- 2026-10-11: **Accepted** by the Builder of #574. This record changes no
  ratified spec row and removes no evidence requirement: every seed is still
  recorded, the harness still owns it, and no record is reclassified. It
  withdraws an exact-replay expectation that the measured simulator does not
  meet. That is the same self-ratification basis DR-0012 used for its own
  methodology and claim-boundary rules. It does not supersede DR-0012; it
  states how DR-0012's "independent seeds" wording reads for `trnoise`
  sources (see Decision, point 3).

## Context

`sim/README.md` rule 2, "No seed, no evidence", says a transient-noise record
without its seeds is unreproducible, which implies that with its seeds it is
reproducible. The harness writes one `.option seed=<n>` per run and refuses
competing seed controls (#566).

The seed-control experiment
(`sim/tool-experiments/2026-10-11-ngspice-seed-control/`) found that two
ngspice-46 processes with the same `.option seed` produced different
`trnoise` waveforms, while the `agauss` parameter and the control-language
`sgauss` draws repeated exactly. #574 asked whether any ngspice-46 control
makes the noise seed-controlled.

The follow-up experiment
(`sim/tool-experiments/2026-10-11-ngspice-trnoise-seed-replay/`, ideal
elements only, no PDK, 18 sequential processes, all exit 0) measured, on the
ngspice-46 build it identifies:

- under the harness start-up policy (`-n`, `SPICE_SCRIPTS` at a snapshot of
  the pinned `spinit`), and with each of `setseed N` or `set rndseed=N` in an
  explicitly supplied `spinit`, `setseed N` in a user `.spiceinit` (the
  manual's suggestion, section 11.3) and a control-block `setseed N`, two
  processes with the same seed shared none of 16 `trnoise` samples. Sentinels
  confirmed the start-up files were read;
- the same seed always reproduced the `agauss` and `sgauss` draws;
- run as process 1 in a new PID namespace (a diagnostic, not a control), the
  noise repeated exactly and was identical for seeds 11 and 12.

So in this build the seed does not reach the `trnoise` white-noise
generator, and two runs are different noise realizations because they ran
as different processes. Source reading agrees: `initw()` seeds that
generator from `getpid()` after the start-up files are read. That source
reading is a hypothesis consistent with the measurement, not something the
experiment measures.

## Decision

We will treat a transient-noise record's "How to reproduce" as replay of
its **deck and configuration**, not of its waveforms, and say so in every
new record.

1. **Seeds stay mandatory and harness-owned.** "No seed, no evidence" is
   unchanged for `tran-noise` and `mc`. The harness keeps emitting one
   `.option seed=<n>` per run, keeps rejecting repeated seeds and competing
   seed controls, and records every seed in run order. For transient-noise
   runs the seeds fix the non-`trnoise` random draws (`agauss` mismatch,
   control-language functions) and identify the runs.
2. **Reproduction contract.** Re-running a `tran-noise` record's commands
   at its `repo_commit`, with its input, manifest and start-up snapshots,
   reproduces the deck, the PVT point, the start-up configuration and the
   seeded non-`trnoise` draws. It does not reproduce the `trnoise`
   waveforms, so its measured values are a new sample, not a replay. New
   `tran-noise` records generated by `sim/run_corners.py` carry an additive
   frontmatter block
   (`reproduction: scope: deck-and-configuration`,
   `trnoise_waveform_replay: false`, the experiment path, this record's
   id) and a paragraph in "How to reproduce" saying this. Deterministic and
   `mc` records do not get the block: the limit was measured for `trnoise`
   sources only.
3. **Seeds are not evidence of distinct or independent noise.** Distinct
   seeds alone do not make `trnoise` realizations distinct (measured: same
   process id, different seeds, identical noise). For `trnoise` runs,
   DR-0012's "4 independent seeds per reported PVT point" therefore reads as
   four runs in separate simulator processes, each with a distinct recorded
   seed. This record makes no claim that such runs are statistically
   independent, and no claim that they are not.
4. **Statistical repeatability is a separate claim.** "A re-run agrees with
   this record within its spread" needs its own tolerance and its own
   evidence. Nothing in this record or the experiment demonstrates it, and a
   record must not cite this DR as if it did.
5. **No simulator workaround is integrated.** No tested control works, so
   none goes into `sim/harness/startup.py` or the deck. The pinned `spinit`
   stays free of seed commands.
6. **Existing evidence is untouched.** No record, raw file or experiment is
   edited. Records written before this DR do not have the `reproduction`
   block. Their "How to reproduce" sections should be read under point 2.
   This record does not claim that any existing statistic is wrong.

## Alternatives considered

### Integrate a start-up-file `setseed`

- **What**: put `setseed <n>` (or `set rndseed=<n>`) into a per-run start-up
  script, as the ngspice manual suggests.
- **Why plausible**: it is the documented route to reproducible transient
  noise, and the harness already captures start-up bytes per run.
- **Why rejected**: measured not to work on this build (groups S, R and U of
  the experiment).

### Run ngspice in a fresh PID namespace

- **What**: wrap each launch in `unshare --user --pid --fork` so ngspice
  always runs as process 1.
- **Why plausible**: it made the noise repeat exactly (group P).
- **Why rejected**: it makes every seed produce the *same* noise, so a
  multi-seed record would aggregate copies of one realization. It also
  depends on Linux user namespaces and on a simulator implementation detail.

### Patch or rebuild ngspice

- **What**: seed the Wallace pool from the seed option.
- **Why plausible**: it would make seeds meaningful for `trnoise`.
- **Why rejected**: out of scope for #574 (no patching or distributing the
  simulator). The repo's evidence would also then depend on a private
  build. Raising it with ngspice upstream is listed as follow-up.

### Do nothing

- **What**: keep the README wording and record format.
- **Why plausible**: fresh noise is still a valid sample of the noise
  process, so no recorded statistic is wrong because of this.
- **Why rejected**: records would keep implying an exact replay a reader
  cannot obtain, and seeds would keep implying a distinctness they do not
  provide.

## Consequences

- **Positive**: every new transient-noise record states what its
  reproduction commands can and cannot reproduce. The harness comments no
  longer say the seed governs `trnoise` sources.
- **Negative / accepted cost**: no transient-noise waveform in this repo can
  be replayed sample for sample on this simulator build. A disputed value
  can only be checked statistically, and that needs its own tolerance and
  evidence.
- **Follow-up required**: (a) distinct noise realizations rely on distinct
  process ids, so execution that gives every run the same process id (for
  example one container or PID namespace per run) would silently duplicate
  realizations across seeds. That needs its own guard or check and is
  tracked in #605. (b) Report the behaviour to ngspice upstream
  (an operator action outside this repository). (c) Any statistical
  repeatability claim needs its own experiment.
- **Revisit if**: an ngspice build or control is shown, by a new dated
  experiment, to make `trnoise` repeat for the same seed and differ for
  different seeds. That would justify a superseding DR that restores exact
  replay for records made with that build.
